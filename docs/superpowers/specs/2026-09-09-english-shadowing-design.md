# Shadow — 英语口语影子跟读训练工具

**日期：** 2026-09-09
**状态：** 设计已确认，待实现
**定位：** 本地单用户工具（先给自己用，不做多用户/云端）

---

## 1. 问题诊断

用户的三个症状——「开口不知道说什么」「发音不行」「以前只靠读来学」——是同一个根因的三种表现。

**根因：英语以「视觉/拼写」形式存储，而非以「声音」形式存储。**

通过阅读习得的英语，存储路径是 `拼写 → 意思`。说话时需要走三道转换：`想到中文 → 检索英文词 → 拼出读音 → 发声`。三道转换叠加实时压力，必然卡壳。

母语者的存储路径是 `声音 → 意思`，且存储单位不是单词，而是**成块的句子片段**（"I was gonna say...", "the thing is...", "it kinda depends"）。说话不是现场造句，是调用现成语块。

由此推出三个症状的解释：

| 症状 | 机制 |
|---|---|
| 发音不地道 | 脑中的音是用中文音系近似出来的假音，且逐词等重音、无弱读 |
| 开口说不出 | 有大量「认识但调不出」的被动词汇，且缺乏可直接调用的语块库 |
| 开字幕懂 80%、关字幕掉到 40% | 声音进入后需先还原成拼写才能理解，实时语流下来不及做 |

用户自测确认为 **B 级：开字幕懂 80%，关字幕 40-50%**——典型的视觉依赖，与诊断完全吻合。

## 2. 方法论

有效链路是三段，缺一不可：

```
可理解输入(听) → 影子跟读(模仿) → 强制输出(说)
   建立音感        校准发音+语流       打通检索路径
```

针对 B 级用户的优先级：

1. **Shadowing** — 治发音与语流。模仿对象不是单词发音，而是节奏、连读、弱读、升降调。中国人发音「不像」，80% 不是音标错，是节奏错。
2. **语块采集** — 治「不知道说什么」。目标是攒可直接搬用的整句。
3. **强制输出 + 即时反馈** — 打通最后一公里。无反馈的输出会固化错误。
4. **停止背单词书和做阅读理解** — 这部分已经过量。

**关键判断：v1 不做 AI 自由对话。** 在声音存储建立之前做自由表达，等于用中文思维造句 + 错误发音输出 = 固化错误。市面产品的通病是把最后一步当第一步卖。

### 2.1 与母语习得路径的关系

本设计**刻意只抄一半儿童母语习得路径**。记录取舍依据，避免日后反复纠结。

「像儿童学母语一样学外语」是个陷阱：儿童 5 岁前累计沉浸约 15,000 小时以上，换来的仍是几千词汇、
大量语法错误、无法讨论抽象话题。成年人达到自如交流通常在 1,000-2,000 小时量级。**按每小时产出算，
成年人效率高一个数量级。** 儿童赢在总时长与神经可塑性，不赢在方法效率。

因此目标不是模仿儿童，而是：挑出成年人无法绕过的部分照抄，其余全部用成年人的优势抄近路。

**照抄的三条：**

| 原则 | 儿童表现 | 本设计对应 |
|---|---|---|
| 声音先于文字 | 4-6 年纯听觉期，不识字 | Step 1 强制盲听。**这是用户唯一真正做错的顺序，不可省略** |
| 语块先于语法 | 第一批话是整块的（"wassat" / "gimme"），语法后来自行长出 | Shadowing 装的是语块而非单词 |
| 不经翻译 | 无母语可翻译 | 精听填空与跟读全程不出现中文 |

**故意反着来的三条：**

| 原则 | 为什么不能照抄 | 本设计对应 |
|---|---|---|
| 儿童靠被动浸泡建立音位 | **知觉窄化：婴儿在 6-12 个月间失去分辨非母语音素对立的能力。** 成年人的耳朵已被中文音系格式化，中文不区分的对立被动泡多久都不会自行浮现 | Step 2 挖空弱读词 + Step 4 词级 diff：**把听不见的东西显式指出来** |
| 父母基本不纠语法，儿童靠海量输入自行收敛 | 成年人没有那个输入量去自然收敛。无反馈的重复只会固化错误 | 坚持 B+C 双反馈 |
| 儿童无元认知能力 | 成年人能看懂图表并当场调整，这是可对冲「窗口已关」的核心资产，放弃它毫无道理 | 韵律曲线叠加图——把儿童需数千小时内化的节奏感压缩成可在十秒内读懂的图 |

**已知缺口：泛听（浸泡量）。** 本设计全部是精听——高强度、高专注、逐词抠。而儿童路径中占绝大比重的是
无压力背景输入，它建立的是流畅度而非精度。**只有精听会练成「每个音都准但说话一顿一顿」。**

**决定：不实现泛听模式。** 泛听不需要任何特殊功能，任意播客 app 即可承担，为它写代码是浪费。
用户自行用现成工具完成这部分，本工具专注精听闭环。

## 3. 产品范围

### 做

- 从任意 URL（YouTube / 播客 / 视频）导入素材，自动转写、切片
- 四步训练闭环：盲听 → 精听填空 → 影子跟读 → 双反馈
- 双反馈：ASR 可懂度词级 diff + 韵律曲线叠加
- 收藏语块（仅存储，复习机制留到 v2）

### 不做（v1）

| 不做 | 理由 |
|---|---|
| AI 自由对话 | 声音存储未建立前做输出训练会固化错误 |
| 语块间隔复习系统 | 有价值但属第二阶段，v1 只存不复习 |
| 登录 / 多用户 / 云端 | 定位是本地单用户工具 |
| 音标级发音打分 | 中国人的问题 90% 在韵律不在音标，先解决大头 |
| 自动评分阈值 | 尚无数据支撑合格线，硬编数字会误导。v1 只呈现数据，过不过由用户自己判断 |
| 泛听 / 浸泡模式 | 泛听不需要特殊功能，现成播客 app 即可承担，为它写代码是浪费。详见 2.1 |

## 4. 训练闭环设计

### 4.1 导入（一次性，非每日）

```
URL → yt-dlp 抓音频 → Whisper 转写（词级时间戳）→ 切片 → 入库
```

**切片规则：** 在停顿处切，不在句中切。利用词级时间戳找出词间静音间隔 > 0.4s 的候选切点，凑到 30-90 秒切一刀，保证每个片段是完整语义单元。

一次导入 20 分钟音频约产出 20 个片段。

### 4.2 每日训练：四步

**Step 1 · 盲听**

播放片段，**不显示任何文字**，听 2 遍，用户自评理解度（1-5）。

*设计意图：* 用户的病是视觉依赖，第一道防线就是在看到文字之前强制耳朵单独工作。字幕常开等于持续给病灶续命。

**Step 2 · 精听填空**

显示文本但挖空，用户听着填。

**挖空选词规则：不挖生词，专挖被弱读的功能词。**

- 条件一：属于功能词表（of / have / to / and / been / that / would / a / the / for / can ...）
- 条件二：该词被弱读。判定方式——先按片段内所有词算出「平均每音节时长」作为基准，再对每个词求
  `实际时长 / (音节数 x 基准)`，比值 < 0.6 判定为被吞。音节数用 CMU 发音词典查询，查不到时按元音字母簇数估算。
- 取两者交集，按比值从小到大排序

**挖空数量约束：** 每片段挖空词数不超过总词数的 15%，且下限 3 个、上限 12 个。不设上限会导致整句被挖空，
练习变成猜谜；不设下限则短片段可能一个空都没有。候选不足时放宽条件二至比值 < 0.8。

*设计意图：* 用户听不懂的从来不是大词，而是 "should have been" 被读成 "shoulda bin"。这一步把病灶精确定位并直接呈现。

**Step 3 · 影子跟读**

文本全显示，播放音频，用户跟读并录音，可无限重来。

**Step 4 · 双反馈**

- **可懂度（ASR diff）：** 用 Whisper 转写用户录音，与原文做词级 diff，漏词标红、错词标黄。客观回答「你说的话能不能被听懂」。
- **韵律（曲线叠加）：** 提取原声与用户录音的音高曲线 + 能量包络，经词锚点时间对齐后叠在同一张图上。

**音高必须做半音归一化。** 用户与原声说话人的基频范围可能相差一倍（男声约 100 Hz vs 女声约 220 Hz），
直接叠加 Hz 曲线两条线离得老远，毫无可比性。转换为相对各自浊音段基频中位数的半音数：

```
semitone = 12 * log2(f0 / median_f0_voiced)
```

比较的是**相对起伏（语调轮廓）**而非绝对音高，这正是训练目标。能量同理，减去各自的 95 分位值做归一化。

反馈图为**三面板**：

| 面板 | 内容 | 回答什么 |
|---|---|---|
| Panel 1 | 半音归一化音高曲线叠加（原声实线 / 用户虚线），标注词边界 | 语调轮廓、重音落在哪 |
| Panel 2 | 归一化能量包络叠加 | 轻重分布 |
| Panel 3 | **每词时长比值条形图**（用户时长 / 原声时长，1.0 为基准线），漏词与错词标红 | **节奏**：哪个词拖长了、哪个词吞了 |

*预期呈现：* 原声是波浪线（有起伏、有轻重），用户是锯齿线（逐词发满、平均用力）。
**Panel 3 是治「逐词等重音」的主图**——把「语感」这种玄学变成一张可对齐的图。

**过关判定由用户自行点击。** v1 不设自动阈值。

### 4.3 为什么这个闭环能解决「不知道说什么」

表面上 v1 未做输出训练，但「不知道说什么」的真相是脑中没有可直接调用的成句语块，只有孤立单词，每次开口都要现场造句，而造句需要语法运算，实时压力下必然崩溃。

Shadowing 正是把整块句子连同其声音、节奏一起装进肌肉记忆。练够数百片段后会出现「话自己蹦出来」的调用感。发音改善只是副产品。

## 5. 技术架构

### 5.1 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | Python + FastAPI | 整条链路的工具（yt-dlp、Whisper、语音分析）全在 Python 生态 |
| 前端 | React + Vite | 训练页是 4 步状态机套录音/播放/反馈三层异步；原生 JS 会写成互相纠缠的回调，违反「文件小而聚焦」 |
| 转写 | `mlx-whisper`，模型 `large-v3-turbo` | Apple Silicon 原生（目标机为 M4），原生支持词级时间戳——切片与挖空逻辑均依赖它 |
| 音高提取 | `praat-parselmouth` | 不用 `librosa.pyin`：Praat 音高轨迹在浊音/清音边界更干净；pyin 在弱读轻声处易断裂，而弱读正是要观察的地方 |
| 时间对齐 | **词锚点分段线性对齐**（`numpy.interp`） | 不用帧级 DTW：90 秒片段是 9000x9000 的 DP，8100 万格，纯 Python 跑不动。而 Whisper 对用户录音同样输出词级时间戳，词级 diff 的匹配结果本身就是词对齐——用匹配上的词做锚点做分段线性时间弯折，O(n) 而非 O(n^2)，锚点还带语言学意义。匹配锚点少于 3 个时退化为整体线性缩放。连带不引入 `librosa`（它依赖 `numba`，在 Python 3.13 上有兼容风险，为一个函数背这个包不值） |
| 存储 | SQLite | 单用户本地工具，无需更重的方案 |

**约束：回测用户录音必须使用与转写素材相同的 Whisper 模型。** 用小模型回测会把模型自身的识别缺陷算到用户头上，反馈失真。

### 5.2 模块划分

```
src/shadow/                 可安装包，提供 `shadow` 命令
├── config.py           路径 / 常量（全部经 SHADOW_DATA_DIR 可覆盖，便于测试隔离）
├── models.py           frozen dataclass（不可变）
├── db.py               SQLite schema + 读写
├── media.py            ffmpeg 封装（切片导出、格式转换）
├── cli.py              命令行入口
├── ingest/

│   ├── segmenter.py    词级时间戳 -> 30-90s 片段（停顿处切）[纯函数]
│   └── pipeline.py     串联导入流程 + 状态机
├── drill/
│   └── blanks.py       挖空选词：功能词表 ∩ 弱读比值 [纯函数]

│   ├── prosody.py      音频 -> 半音归一化音高 + 归一化能量包络

│   └── timing.py       匹配对 -> 每词时长比值
└── report/
    └── plot.py         三面板对比图 (matplotlib)

M3 追加 src/shadow/api/（FastAPI）与 web/（React + Vite）。

web/src/
├── App.jsx, api.js
├── pages/         Library.jsx, Import.jsx, Train.jsx
├── train/         BlindListen.jsx, GapFill.jsx, Shadow.jsx, Feedback.jsx
├── components/    AudioPlayer.jsx, Recorder.jsx, ProsodyChart.jsx, WordDiff.jsx
└── hooks/         useRecorder.js, usePlayer.js
```

`analysis/` 四个模块与 `segmenter` / `blanks` 均为纯函数：输入音频/文本，输出数据，不碰数据库与网络。因此可脱离整个 app 单独测试——而它们（时间弯折、时间戳换算、切片边界）正是最容易出微妙 bug 的地方。

### 5.3 数据流

**导入**（一次性，约 1-2 分钟）：

```
URL → downloader → audio.wav → transcriber → 词级时间戳
    → segmenter → 片段[] → blanks → 挖空位置 → SQLite
```

导入是长任务，做成**异步任务 + 状态轮询**：提交 URL 立即返回 source id，前端轮询进度。同步等待会超时。

执行方式用 FastAPI 的 `BackgroundTasks`，进度写入 `sources.status` 字段，取值为
`downloading` / `transcribing` / `segmenting` / `ready` / `failed`；失败时错误详情写入 `sources.error`。
单用户场景下无需引入 Celery 等任务队列。进程重启会遗留卡在中间态的记录，启动时把非终态记录一律标记为 `failed`。

**练习**（每次提交约 3-5 秒）：

```
录音(webm) → ffmpeg → wav ─┬→ transcriber → diff(原文) → 词级红黄标注
                            └→ prosody ─┐
              原声 → prosody ────────────┴→ 词锚点对齐 → 三面板曲线数据 → 前端画图
```

## 6. 数据模型

SQLite，五张表。所有记录**只追加不修改**（frozen dataclass 映射），练习历史天然成为可回溯的进步记录。

```
sources          导入的素材
  id, url, title, duration_sec, audio_path, status, error, created_at

segments         切好的训练片段
  id, source_id, idx, start_sec, end_sec, text, words_json

practice_runs    一次完整的 4 步训练
  id, segment_id, blind_rating(1-5), gapfill_correct, gapfill_total,
  started_at, finished_at

attempts         一次跟读录音（一个 run 下可有多次）
  id, run_id, audio_path, asr_text, diff_json, prosody_json, created_at

saved_phrases    收藏的语块
  id, segment_id, text, created_at
```

`segments.words_json` 存词级时间戳数组（每个词的 word / start / end / 是否挖空）。它总是整块读写，拆成独立表只会换来一堆 join，无收益。

磁盘布局，数据与代码分离：

```
~/.shadow/
├── shadow.db
└── audio/
    ├── sources/<id>.wav
    └── attempts/<id>.wav
```

## 7. 错误处理

外部依赖是这类工具最容易翻车的地方，四个必须显式处理的点：

| 场景 | 处理 |
|---|---|
| yt-dlp 失败（视频下架 / 地区限制 / 需登录） | 捕获退出码，将 yt-dlp 原始 stderr 原样呈现。包装成通用「导入失败」等于扔掉唯一有用的诊断信息 |
| 转写超时 / OOM | 导入前先查时长，**超过 60 分钟直接拒绝**并说明原因，不让用户等 10 分钟才发现失败 |
| 麦克风权限被拒 | 前端明确提示「需要麦克风权限」并给出 macOS 系统设置路径，不静默失败 |
| 录音过短 / 静音 | 提交前检查时长与 RMS 能量，不达标就地拦下，不浪费一次转写 |

**输入校验：** URL 仅接受 http/https scheme；素材时长上限 60 分钟；录音时长下限与能量下限。

## 8. 测试策略

- **纯函数模块（`analysis/` 四个 + `segmenter` + `blanks`）——单元测试，重点。** 切片边界、挖空选词、时间弯折都是易错且不易被肉眼发现的逻辑。音频相关测试用程序合成的正弦波作 fixture，不依赖外部素材。
- **`ingest/`** ——外部依赖打桩测编排逻辑；另留一个打真实网络的集成测试，默认跳过。
- **前端 4 步状态机** ——测状态转换，不测像素。

## 9. 交付顺序

| 阶段 | 内容 | 验证什么 |
|---|---|---|
| M1 | 导入链路，纯 CLI 无界面：URL → wav → 转写 → 切片 → 入库 | 转写质量、切片准确性 |
| M2 | `analysis/` 三模块 + 单元测试；CLI 接受「原声片段 + 用户录音」两个 wav，用 matplotlib 输出一张叠加对比 PNG | **核心假设验证点** |
| M3 | FastAPI 串联，异步导入任务 + 轮询 | 接口连通 |
| M4 | React 前端，四步训练闭环 | 完整体验 |
| M5 | 错误提示打磨、收藏语块按钮 | 可用性 |

### 为什么 M2 排在前面

整个设计押注于一个假设：**音高曲线叠加图真的能让用户看出自己哪里读得不对。**

这个假设可能为假——曲线噪声可能过大、DTW 在语速差异大时可能错位、图可能根本没有信息量。

M1+M2 完成后，**在写任何一行 UI 之前**即可在命令行录一句、生成一张图并自行判断其信息量：

- 有信息量 → 继续 M3
- 无信息量 → 退回重新设计反馈方式（改为关键词级重音标注，或仅保留 ASR diff）

代价是几百行分析代码，而非一整个前端。这是本项目最大的技术风险，因此排在最前面引爆。

## 12. M2 验证后的反馈层重做（2026-09-09）

原设计的三面板曲线图经真实使用验证**无信息量**，已删除。详见
`docs/superpowers/plans/2026-09-09-m2-verdict.md`。

### 失败的根因

使用者原话：「曲线和单词没办法对上，不知道是哪个词快了哪个词慢了。」

不是半音、归一化这些概念难懂，而是**曲线上任何一个位置都无法对应到一个词**。
看到一段下坠的线，不知道那是 `life` 还是 `That's`，自然也就不知道该改什么。

还有一层方法论上的错误：使用者的根本问题是英语以视觉形式存储，而反馈却是一张图——
**用视觉手段修听觉毛病，重复了那个老毛病**。反馈必须以可执行的指令为主。

### 新设计的两条原则

1. **图上每个元素都必须挂在一个词上。** 没有脱离单词的连续曲线。
2. **一张图只编码一个变量。** 把时长、音高、能量塞进同一组曲线是失败的另一半原因。

### 交付形态

| 组件 | 内容 |
|---|---|
| 文字诊断 | 排序后的可执行指令，「下一遍改这 N 处」，说清改哪个词、怎么改。**这是主要出口** |
| 图 1 · 节奏 | 真实秒数轴，块宽 = 时长，空隙 = 真实停顿，标出漏掉的停顿与累积落后 |
| 图 2 · 音高 | 一词一格叠加，虚线框 = 原声、实心 = 用户，块的斜度 = 词内升降 |
| ASR diff | 保留。漏词/错词列表是硬指标，且能明确排除「音素层面有问题」这一类担忧 |

### 一个必须分开算的量

**发声时长与停顿时长要分别统计。** 实测用户发声慢 16%、停顿少 40%，
总时长只差 8%——两个偏差方向相反，在「整体语速」这个数字上完全抵消。
只报总时长会把真正的问题藏住。

### 连带删除

`analysis/align.py`（词锚点时间弯折）与 `analysis/timing.py` 已删除：
新设计中图 1 用真实时间轴、图 2 用逐词格子，都不需要时间弯折。
